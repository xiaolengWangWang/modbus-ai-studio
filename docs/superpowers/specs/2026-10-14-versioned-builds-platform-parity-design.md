# 2.0.0 版本化构建与平台差异说明设计

## 目标与范围

将共用源码、构建脚本和各版本构建产物明确分开。下一目标版本统一为 `2.0.0`。Windows 同版构建标准桌面版与兼容版；两者都是功能对照基准，其中标准版代表共用桌面功能，兼容版另提供旧版 Windows 和 Mesa 软件渲染支持。macOS 桌面版和 Linux Web 版的每个发布包旁都输出一份 Markdown 差异说明，作为该平台后续优化的依据。`modbus-cli` 不参加这项功能对照。

现有 `cmd/`、`internal/`、`platform/`、`assets/`、`tests/` 是共用源码和资源，`build/` 与 `.github/workflows/` 是共用构建流程。保持这些目录与 Go 包路径不变。构建产物不提交到 Git，按版本保存在 `dist/vX.Y.Z/`，并通过 GitHub/Gitee Releases 留存发布副本。

## 版本与目录

```text
docs/platform-parity/macos.md       # macOS 桌面版差异的可维护源文件
docs/platform-parity/linux-web.md   # Linux Web 版差异的可维护源文件
dist/v2.0.0/                         # 2.0.0 安装包、校验值、发布记录和差异 MD
dist/v1.5.0/                         # 迁入现有的 1.5.0 本地产物，原样保留
```

所有构建、冒烟测试、CI 工件下载和发布工具都使用相同的版本目录。`VERSION=x.y.z` 只选择输出目录及已校验的版本号，不允许把 2.0.0 代码标成其他版本。旧版本目录不因发布新版本自动删除；清理命令只处理明确选定版本的临时文件，不删除历史安装包、校验值或发布记录。对现有 `dist/` 的迁移只移动文件名明确包含 `1.5.0` 的产物，保留未分类的本地辅助文件，遇到目标文件同名且内容不同即停止。

## 差异文档

源文件在对应维护分支随代码修订，并由构建流程为以下四个包输出同名附加文件 `<安装包文件名>-differences.md`：

1. `ModbusAIStudio-2.0.0-macOS-Intel.dmg`
2. `ModbusAIStudio-2.0.0-macOS-AppleSilicon.dmg`
3. `ModbusAIStudio-Web-2.0.0-Linux-x64.tar.gz`
4. `ModbusAIStudio-Web-2.0.0-Linux-arm64.tar.gz`

每份 Markdown 标明目标版本、目标包、Windows 基准版本和检查日期，列出两者实际功能状态。对 Windows 有而目标平台没有的功能，记录原因、处理决定（`补齐`、`暂缓`、`不适用`）和验证依据；对目标平台独有功能单列说明。共用平台的两种架构可使用同一源文件，但输出文件名各自对应安装包。文档内容由维护者核对代码、测试与实际构建后更新，构建过程只填版本与包名，不自动猜测功能差异。缺失、版本不符、模板未填完或密文文档会使发版准备失败。四份文件随安装包上传到 GitHub/Gitee Releases，并写入发布清单与 SHA-256 校验。

## 开发与维护规则

- 通用功能和共用协议逻辑在 `main` 的核心代码实现，同步更新受影响平台的差异源文件。
- 已发布版本的缺陷从对应版本 tag 创建 `maintenance/v主版本.次版本` 维护分支，只在该分支修复与发布补丁版本。例如 2.0.0 的修复发布为 2.0.1；需要覆盖 `main` 时再单独移植修复，避免把新功能带进维护版。
- 平台专有的缺陷或补齐工作在目标维护分支修改该平台代码和差异说明，不复制整套核心源码。
- 每次发版对照差异文档完成状态更新；`暂缓` 项保持可追踪，`不适用` 项写明平台限制或产品形态原因。

现有发版工具把 GitHub 打包引用和 Gitee 镜像目标写死为 `main`。改造后，发版工具只接受当前 `main` 或 `maintenance/v主版本.次版本` 分支，并核对 GitHub 上同名分支指向当前提交；CI 在该分支打包，Gitee 同步到同名分支，tag 仍指向该提交。维护版发布不得改写 GitHub 或 Gitee 的 `main`。

## 验收

1. 2.0.0 的构建脚本、CI、冒烟测试和发布工具都指向 `dist/v2.0.0/`；发布 2.0.0 后 `dist/v1.5.0/` 不被清理。
2. 四种非 Windows 包各有一份匹配版本的差异 Markdown，`modbus-cli` 和 Windows 包不额外生成。
3. 发版准备拒绝缺失、版本不符、未完成或密文的差异文档；清单和校验值覆盖四份 Markdown。
4. 从 `maintenance/v2.0` 准备 2.0.1 时，远端分支、CI 引用和 Gitee 镜像都使用 `maintenance/v2.0`，两端 `main` 不变。
5. 发版工具测试、脚本语法检查及可运行的本机冒烟测试通过。完整 Go 测试中现有的 `TestReadWindowsPreferMoreSpaceForRegisters` 布局失败单独记录，不归入目录调整；实际发布仍需现有 CI 门禁通过。

本设计只调整目录、发版流程和平台差异记录；发布 2.0.0 本身需在改造完成并验证后执行。
