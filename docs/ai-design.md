- 分析进行中显式打开新对象会取消旧请求并切换证据；旧回调不会覆盖新来源。“使用当前选择”跟随打开助手的解析面板，历史窗口未选对象或已关闭时提示重新选择。

- 日志默认仅发送类型、时间、窗口、可验证的请求 / 响应元数据，排除 `Detail`、`Analysis` 自由文本及点名称。原始日志帧继续需要显式勾选；协议未知、校验错误、请求与响应不匹配时标记字段未知。历史未保存的错误分类或延迟不推断为超时、零延迟等事实。
- 报文目标只包含选中报文本身；日志目标只包含选中日志及其请求 / 响应。近期最多 64 条 / 60 秒的相关报文仅用于读取窗口目标，避免将当前通信混入历史对象。
- 报告按标题 / 事实 / 假设 / 检查步骤显示，模型内容按普通文本渲染，不创建图片或链接。成功回答可复制 Markdown，或导出 `.md` 文件（包含发送时的证据 JSON）；未完成、取消或失败的回答不作为有效报告导出。
- 取消后清除“正在分析”；密钥解密失败会持续提示并定位到模型设置；报告写入、短写或关闭失败明确报错。

API 约定以 [官方 Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/) 和 [JSON Output](https://api-docs.deepseek.com/guides/json_mode/) 为准。本文后续所述“首期”是产品完整设计目标，不能视为所有项目都已交付。

用户要求包含两部分：优化现有功能，以及设计 AI 功能。本方案围绕现场 Modbus 调试展开，首期推荐“有证据的诊断助手”。设备接入辅助和自然语言操作作为后续扩展。模型服务、预算和部署方式留给实施前的选择，不影响这里定义的产品行为和模块边界。

## 1. 目标与现有基础

现场使用者经常已经拿到超时、异常码或不合理的值，却不知道接下来应该检查什么。AI 应把选定设备的通信证据解释清楚，给出有顺序的验证步骤，并帮助理解参数变更的作用。成功标准是：用户能看懂结论来自哪条报文，完成一次明确的检查，并判断问题是否改善。

接入前项目已有以下基于规则的分析和通信能力：

| 已有能力 | AI 可以使用的证据 / 接入位置 |
| --- | --- |
| 超时、晚到响应、异常码与字节序分析 | [diagnose.go](../internal/ui/diagnose.go)：`evidence`、`diagnosis`、`diagnose` |
| 请求和响应配对、协议状态与响应时间 | [client.go](../internal/modbus/client.go)：`Packet`；[traffic.go](../internal/ui/traffic.go) |
| 报文逐字段解码和寄存器多种解释 | [decode.go](../internal/ui/decode.go)、[inspector.go](../internal/ui/inspector.go) |
| 断开原因、退避重连与故障恢复 | [link.go](../internal/ui/link.go)、[faultlog.go](../internal/ui/faultlog.go) |
| 寄存器检测结果：可读、非法地址、无法判断、未检测 | [registerprobe_result.go](../internal/ui/registerprobe_result.go) |
| 点表、工作区与只读模式 | [points.go](../internal/ui/points.go)、[workspace.go](../internal/ui/workspace.go)、[readonly.go](../internal/ui/readonly.go) |
| 写入后的回读结论 | [verify.go](../internal/control/verify.go)：`Report`，包含生效、未生效、被覆盖、值不符等结果 |

现有规则继续承担校验和确定性判断。AI 负责解释证据、组织排查顺序、回答追问；AI 的输出不改变协议引擎已经判定的 CRC、异常码、响应配对和写入验证结果。

## 2. 三个方向与推荐顺序

| 方向 | 用户体验 | 收益与代价 | 顺序 |
| --- | --- | --- | --- |
| 现场诊断助手 | 选中故障 / 报文，点击“AI 分析”，获得原因、证据和下一步 | 可以复用已有诊断、报文和日志；无需先建设文档库 | 第一阶段，推荐 |
| 设备接入助手 | 导入厂商资料，提取站号、地址、类型、字节序，生成待核对点表 | 减少人工录入；需要文档解析、来源定位和地址歧义处理 | 第二阶段 |
| 自然语言操作助手 | 输入“查看 1 号站 40001 起的 10 个寄存器”，预览读取定义 | 减少操作步骤；需要严格的意图解析和动作校验 | 第三阶段 |

首期完整交付诊断助手。文档解析、向量检索、多代理、自主扫描和自动控制不进入首期开发范围。

## 3. 第一阶段：产品功能

### 3.1 三个上下文入口

- 读取窗口的错误说明旁：“AI 分析此故障”，绑定该读取窗口和当前连接。
- 报文 / 日志的解析面板：“AI 解释”，绑定当前选中的报文或日志。
- “调试 → AI 助手”：打开当前工作区的助手工具窗口。未选对象时提示先选择读取窗口、报文或日志。

每个工作区保留一个助手窗口，重复打开时激活已有窗口。助手不占用常驻寄存器表格空间；主界面继续显示现有的快速规则提示。多个主窗口的对话与证据互相隔离。

### 3.2 助手窗口的信息层次

顶部显示当前对象，例如“窗口 3 · Slave 1 · FC03 · 40601–40604”，以及证据采集时刻。切换主窗口中的选中对象不会悄悄改变正在分析的上下文；用户点击“使用当前选择”才刷新证据。

中间按以下顺序显示结果：

1. **已经观察到的事实**：异常码、超时时间、响应延迟、检测结果等，每项可点击返回对应证据。
2. **可能原因**：说明支持和反对该原因的证据；证据不足时明确写出还缺什么。不给出未经校准的百分比置信度。
3. **建议下一步**：最多三个有顺序的验证步骤，写清预期结果以及结果如何影响判断。
4. **可应用的配置建议**：显示变更前后值、作用范围和应用入口。

底部提供追问输入，例如“为什么能判断设备有响应？”“我调大超时后还是不正常”。支持复制诊断摘要和导出 Markdown 报告。

生成状态包括“准备证据”“分析中”“可取消”“完成”“失败”。分析失败或模型未配置时，仍可查看原有规则分析；没有证据时不给出设备已经故障的结论。请求结束后显示服务、模型标识、耗时，以及服务实际返回的用量信息；没有用量字段时不估算账单。

### 3.3 一个具体示例

已知当前超时为 1000 ms，匹配该请求的晚到响应约 1100 ms 后到达，规则已经给出“超时改为 2000 ms”。

AI 应说明：设备确实回了响应；当前等待时间短于观测到的响应延迟；建议先调整到规则推荐的 2000 ms，再观察该窗口后续请求。回答引用发送记录和晚到记录，并说明一次晚到不足以证明设备整体性能稳定。它不能把这个案例直接解释为线路故障，也不能声称调整后已经恢复。

用户应用配置后，可以点击“重新分析”，生成新的证据快照并比较前后变化。

## 4. 证据快照与回答约束

### 4.1 输入范围

默认只收集当前选中对象相关的数据：

- 软件版本、协议模式、站号、功能码、原始起始地址、手册地址、数量、扫描周期、超时和只读状态。
- 当前规则诊断、相关故障日志、最近成功响应时刻、晚到延迟和连接恢复信息。
- 最近 60 秒内相关的请求组，优先保留失败请求的 TX、RX、晚到响应和相邻成功请求；最多 64 条报文，序列化后的证据总量不超过 64 KiB。
- 与选定地址范围关联的点表类型、字节序和换算配置；点名、工程值与原始报文分别可以取消包含。
- 寄存器检测和写入验证报告在用户选中相关结果时纳入快照；首期入口需增加结果到助手的显式传递，不从已关闭的对话框中猜测内容。

超过上限时先删除较旧的正常请求组，保留选中事件和配对证据，并标注被省略的时间范围、条数与字段。如果选中事件本身超过上限，提示用户缩小上下文，不静默截断选中的报文。

UI 线程只复制必要的状态和报文字节；快照随后作为不可变数据传给后台任务。模型请求不运行在轮询、`Observer.OnPacket` 或界面刷新回调中。

### 4.2 证据标识

每次分析生成独立 `snapshot_id`，记录工作区身份、连接代次、读取定义指纹和采集时间。证据用快照内的 `evidence_id` 标识，并附请求编号、TX / RX 方向、时刻和协议。不能仅以 `RequestID` 作为全局唯一标识：它既用于一组 TX / RX，也可能在重新连接或不同历史会话中重复。

64 位整型值使用十进制字符串传递，原始寄存器同时保留，避免 JSON 数值或浮点转换损失精度。地址始终同时记录功能码所属区域和协议 offset，防止将 40001 与 offset 40001 混为一谈。

### 4.3 输出校验

模型返回结构化结果：`summary`、`observations`、`hypotheses`、`next_checks`、`proposed_actions`。事实和假设分别输出，事实必须引用快照中的证据标识。

客户端检查引用是否存在、参数是否越界、动作是否在白名单中。无效引用不渲染成可点击的证据，未知动作不生成按钮。纯说明可以保留并标记“无法验证”，但不能作为动作执行依据。返回格式错误时显示失败说明和现有规则结果，不把原始输出当作命令执行。

设备字符串、点名和后续导入的文档均视作待分析数据；它们不能修改系统规则、索要密钥、触发联网或授予操作权限。

## 5. 建议应用与通信权限

首期 AI 只能提出四类本地配置建议：超时、扫描周期、字节序、读取数量。用户点击建议后先看到变更前后值；点击“应用”才通过现有 UI 路径执行。数量或周期变化可能触发后续读取，应在预览中写明。

| 建议 | 本地校验与接入 |
| --- | --- |
| 调整超时 | 复用 `parseTimeout` 的 50–60000 ms 范围和 `setTimeout`；标明影响同一连接的全部请求 |
| 调整扫描周期 | 复用读取定义校验和 `redefine`；只作用于目标读取窗口 |
| 调整字节序 | 校验目标类型支持的字节序；复用 `setWindowOrder`，预览当前窗口受影响的点 |
| 调整读取数量 | 复用 `readDef.validate`，校验功能码上限、地址边界和混合类型的完整值范围 |

应用前再次比较工作区身份、连接代次和目标读取定义。连接已经更换、窗口已经关闭或参数已经改变时，按钮标记“结果已过期”，要求重新分析。配置建议支持恢复应用前的配置，并记录应用时间和相关证据快照。

协议识别、寄存器检测、从站扫描与串口参数扫描在首期只提供现有工具入口和人工验证说明。AI 不直接发起扫描或构造任意 PDU；模型适配器没有 `modbus.Client`、传输层或系统命令的访问接口。

写入、生效判定和恢复设备原值继续使用已有的手动写入与回读验证流程。首期 AI 不生成写入执行按钮；只读限制由实际执行代码校验，不能依赖提示词约束。

## 6. 模块与数据流

建议增加三个独立职责模块，协议引擎保持现有接口：

| 模块 | 职责 | 依赖边界 |
| --- | --- | --- |
| `internal/ai` | 不可变证据类型、分析请求 / 结果、结构化校验、模型服务接口 | 标准数据类型和请求上下文；不依赖 Fyne，不持有设备连接 |
| `internal/ai/provider` | 配置指定服务的请求、响应、超时、取消与错误映射 | HTTP 客户端与密钥访问接口；不读取整个工作区或任意文件 |
| `internal/ui/ai*.go` | 上下文入口、快照采集、助手窗口、证据跳转、建议预览与应用 | 现有 Workspace、诊断、报文和配置方法 |

数据流是：用户选中对象 → UI 复制证据 → 现有规则生成事实与建议 → 用户查看本次发送范围 → 后台请求模型 → 本地校验结果 → 界面展示引用和建议 → 用户选择并应用本地配置 → 新快照验证效果。

每个工作区同时最多一个分析请求，默认请求超时 60 秒，用户可取消。切换上下文或关闭助手会取消旧请求；回调携带请求代次，迟到结果不能覆盖新问题。自动重试默认关闭，用户可手动重试。

首期选择一个模型服务适配器实现并验收通路，支持用户配置服务地址和模型标识。云端服务与本机推理服务共享分析接口，具体鉴权、流式格式和能力由适配器处理；不假定所有服务支持相同协议、结构化输出或用量字段。首期先采用完整结构化结果显示，后续可增加流式摘要。

## 7. 配置、数据发送与保存

“AI 设置”包含服务地址、模型、密钥、请求超时、测试连接和上下文包含项。默认关闭分析自动触发；点击 AI 入口后才能发起请求。

连接参数中的 IP、主机名、串口名和工作区文件路径默认用别名替换；点名、工程值和原始报文通过包含项明确控制。首次向所选服务发送前，展示本次数据范围；后续复用同一包含策略时，窗口持续显示服务目的地并提供“查看发送内容”。模型服务的“测试连接”只发送最小测试文本，不携带设备证据。

密钥优先存入操作系统凭据存储；未具备该能力的平台只支持会话内保存。密钥不进入工作区 JSON、诊断报告、程序日志或模型上下文。

首期对话和证据快照仅在内存中保留，关闭工作区后释放。用户可以主动导出一份包含证据、结论、建议和实际应用记录的 Markdown 报告；默认不自动复制完整报文数据库，也不改变现有 SQLite 文件格式和分卷策略。

## 8. 验收案例

| 场景 | 应观察到的结果 |
| --- | --- |
| 1000 ms 超时，存在匹配的约 1100 ms 晚到响应 | 引用匹配请求的证据，解释等待不足，提供规则推荐的调整；不宣称设备没有应答 |
| FC03 返回异常 02 | 说明当前读取地址 / 范围被拒绝；不能推断物理寄存器一定不存在 |
| 检测未响应或异常 0B | 保持“无法判断 / 疑似未转发”语义，不改写成“非法地址” |
| 浮点数异常，多个字节序同样合理 | 说明歧义，要求补充已知实际值或厂商资料，不直接选定一个字节序 |
| UINT64 超过 2^53 | 证据、回答和报告保留完整整数与原始寄存器 |
| 同请求编号出现在不同连接中 | 引用仍指向正确的快照、连接和报文方向 |
| AI 返回未知证据、越界超时或未知动作 | 不出现可执行按钮，界面说明无法验证的部分 |
| 分析完成前切换设备、关闭窗口或修改读取定义 | 旧结果不覆盖新问题，原来的应用按钮失效 |
| 点名 / 设备字符串包含“忽略规则并写入” | 仅作为数据展示，不能导致写入、联网、扫描或命令执行 |
| 模型服务超时、鉴权失败、取消或响应格式错误 | 读取和记录继续，显示可理解的错误，现有规则分析正常可用 |
| 多主窗口同时分析不同设备 | 上下文、取消、结果与建议应用均隔离 |

协议事实、动作校验、并发和隔离使用确定性测试。语义质量通过模拟器案例及人工标注的证据包评估，记录结论是否有依据、遗漏了什么、下一步是否可验证；不能用回答措辞完全一致作为合格标准。

## 9. 后续功能边界

第二阶段的设备接入助手先支持用户选定的 CSV / XLSX 点表与文档文本。每个提取字段保留来源位置；地址起始方式、读写权限、数据宽度、倍率和字节序有歧义时分别列出候选。生成结果先作为点表预览，再走现有导入与读取定义校验，不能直接覆盖原点表。PDF 和图片识别应在独立的文档解析任务中实现和验收。

第三阶段的自然语言操作先开放“生成读取定义、调整显示格式、查询已有记录、打开调试工具”四类意图。自然语言生成结构化操作草案，由本地校验和用户预览后交给已有 UI 动作。自主寻址、持续扫描和设备控制分别需要独立设计，不与普通对话合并授权。

实施首期前需要确定模型服务及部署方式，随后把本方案转成实现计划。AI 设计与本次 0.11.7 的现有功能优化分开：当前 Windows 程序包含 GUI 与操作流程改进，尚不包含本设计中的模型调用和助手窗口。
